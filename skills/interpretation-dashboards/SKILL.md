# Interpretation dashboards

A bare result figure asks the reader to simulate the alternatives in their head. A dashboard **renders** them — each through the *same plot function* as the result — so "which world is this?" becomes a visual match, not a feat of memory. Every headline analysis ships a dashboard, not a bare figure; exploratory plots are exempt.

## The three rules

1. **Schematics come from the result's own plot function, fed idealized data.** For each competing hypothesis, synthesize data embodying it and push it through the exact plot function used for the real result — never a hand-drawn cartoon. This buys comparability (same axes/encoding), honesty (shows what the method *would actually render*, noise and ceiling included), and method validation (if the idealized effect doesn't produce a visibly distinct plot, the analysis cannot detect it — learn that before a false claim). The generators are the same fixtures that test the analysis.
2. **Self-documenting.** On the figure or page: the **concept** (what is tested, why), **metric definitions** (each axis, its assumptions and ceilings), and an **auto-derived verdict** computed from the data (a classifier returning e.g. `same_operator` / `rotation` / `underpowered`), never asserted by hand. If reading it needs an external methods section, it is not done.
3. **Show the honest nulls.** The schematic row must include the null and the underpowered/uninformative cases, rendered like the live hypotheses — so a flat result reads as a *positive match to a named world*, not as absence. Distinguishing equivalence from failure-to-reject from underpowered is the row's first-class job.

## Layout and process

Schematic row (the menu of possible worlds) directly adjacent to the result in identical encoding; concept/metric text alongside; verdict highlighted; reading path *possibilities → reality → reading*. Process: (1) enumerate hypotheses incl. null + underpowered, one-line meaning each; (2) one generator per hypothesis → result plot function → schematic (reuse test fixtures); (3) real data through the same function; (4) compose. Panel craft: `scientific-figures` skill.

## The dashboard's home is a narrated notebook

The real deliverable is a **narrated results notebook** (marimo): each headline analysis is a section pairing its dashboard and the raw views behind it with the concept, metric equation(s) (LaTeX in `mo.md`), references, stated expectation, and candidate reading. Thin cells, all prose in markdown cells, no analysis logic in the notebook, provenance line at top, long renders cached, `marimo export html` wired into the justfile. Standalone figure files are *exports* of the same `src/` functions — build artifacts, not the deliverable. Litmus test: a collaborator with no prior exposure follows question → method → competing hypotheses → result → candidate reading with no second document.

## Prose and captions: finite working memory

Narration follows the finite-working-memory rules (CORE): plain-language names with the
internal label given once in parentheses, every recurring term re-glossed in each section,
every number carrying its yardstick in the same sentence. "K5-own beats K5-own-shufPC by
+0.4e-4" fails; "each subject's own semantic axes beat their shuffled twin by +0.4×10⁻⁴
held-out R² — about twice the shared-axes residue, a tenth of what the human-judgment band
was worth" passes.

## Checklist

- [ ] Headline analyses ship a dashboard; schematics generated by the result's own plot function.
- [ ] Null + underpowered among the schematics; verdict auto-derived and framed as a candidate reading.
- [ ] Concept + metric text on the artifact; caveats shown, not dropped; absolute *and* relative views.
- [ ] Generators shared with test fixtures; lives in a narrated marimo notebook.
- [ ] No bare config labels in prose or captions; terms re-glossed per section; numbers carry yardsticks.
